# Canonical monetary operations

`Kernel.ResourceMoneyOperationDomain` prepares typed monetary operations over the deployment's actual canonical ResourceBook. It does not introduce an account-balance scalar write, alternate ledger, host evaluator or debit authority.

The explicit order is funding first, application operations second. `sampleFunding` binds the exact original physical Book root and canonical cell law, then checks the domain's unique `(account, asset, balance)` table against the actual Book after the validated compute funding burn. A Nat sample requires account membership and exact equality to `Int.ofNat balance`; a negative issuer balance cannot be truncated into this profile. Repeated role references may share an authenticated sample. Conflicting samples or repeated coordinates in the sample table fail closed.

`prepareFrom` retains that same original loaded Book and funding token, admits the ordered application operations against the funding post, and builds one accepted canonical batch containing funding plus application operations. Every debit sees the actual preceding operations. Transfers, issuer-backed mint, burn, fee and lease retain the existing canonical operation semantics and conserve the total for every asset. The original and final canonical Book laws are checked, including account support.

The resulting `Prepared.writes` contains at most one Book write, with the original physical pre-root and exact canonical final bytes/root. An empty combined batch retains the original Book read guard. `withQuotaWrites` combines this final Book write with the actual Pay usage post. A caller must use it in place of the old accounting Book write; appending both would create two competing writes to the same Book.

The native world receiver still supplies the checked source-plan relation, exact source input, actual signed payer and every debit capability, current account law, source/policy guards and participant authorization. Monetary preparation alone is not an accepted invocation. Settlement must place the room's guarded round/phase transition and return commitments into the same selected durable intent as Book and Pay. The existing invocation nullifier, admission, durable receiver and exact receipt resolve retry before funding again. A still-solvent Book does not authorize replay of a settled market.

The additive assurance module checks kernel axiom accounting and general refuters: stale original root, a fabricated sample balance, a missing account and a later debit that overdraws an intermediate Book. These establish properties of the actual preparation token. End-to-end source execution, signed authority, atomic room settlement and native replay require the joined world consumer qualification; they are not inferred from module compilation.
