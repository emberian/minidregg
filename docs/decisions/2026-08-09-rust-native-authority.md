# Rust native authority boundary

Status: accepted 2026-08-09.

## Decision

Lean is the only source of statements, semantic relations, protocol schedules,
security profiles, and acceptance. Rust may expose generated data transport and
fallible arithmetic over caller-supplied buffers. A handwritten Rust API must not
select a proof-system relation merely because its output is later rechecked.

The public `logup256_kernels` module crossed that boundary: it selected the
fraction, Booleanity, and quadratic round polynomials and supplied a
round-interpolation API without a generated Lean call descriptor. Those APIs are
deleted. The surviving module is named `tower256_kernels` and contains only
generic scatter, dot-product, equality-weight, affine/MLE, and rational-pair
reduction operations. It has no LogUp statement, round-message, transcript,
proof, verifier, or acceptance type.

## Hard invariants

- Native success returns candidate buffers, never evidence or an acceptance bit.
- Native failure may affect availability or completeness only.
- Rust does not parse a semantic request or construct a receipt/history entry.
- A protocol-shaped native operation requires a Lean-emitted bounded descriptor;
  a suggestive module comment or caller-supplied challenge is not enough.
- Cross-language tests are diagnostic. They are not refinement, because Rust has
  no project semantics to refine.

## Exact surviving ABI surface

Generated by Lean:

- `semantic_artifact_v1`: canonical artifact bytes and identifier/count data;
  opaque `WorkRequestDto`, `KernelBufferDto`, `NativeErrorDto`, and
  `NativePlanDispatch`. This is emitted data/plumbing, not a handwritten semantic
  model. No dispatch implementation is currently connected to a kernel.

Handwritten, opaque candidate computation:

- `babybear` and `field6`: BabyBear modulus/2-adic constants and the six-lane
  `u^6 = 31` coordinate arithmetic;
- `binary_tower` and `binary_tower_256`: explicit Fan--Paar coordinate arithmetic,
  byte encoding, and basic additive-fold arithmetic;
- `additive_ntt`: caller-parameterized forward/inverse additive transforms;
- `mle_kernels`: generic MLE/Mobius/dot operations plus GF(2^64), GF(2^256),
  and Ext6 transform/fold specializations;
- `tower256_kernels`: generic scatter, vector, equality-weight, MLE, and
  rational-pair reduction operations; and
- `hash_kernels`: raw caller-customized cSHAKE256 XOF.

The BabyBear/Ext6 constants, Fan--Paar bases and limb codecs, additive transform
order, specialized MLE fold conventions, and cSHAKE algorithm are still
Rust-selected profile-shaped ABIs. They are untrusted and are not yet invoked
through exact generated Lean descriptors. Their output cannot reach acceptance
without a Lean-owned check. This is the remaining native representation debt.

## Rejected alternatives

- Keeping protocol-named round helpers because every challenge was caller
  supplied: the helpers still authored the relation polynomial and round shape.
- Calling empirical Rust/Lean vector agreement a proved refinement: there is no
  authoritative Rust semantics or cross-language theorem.
- Deleting all arithmetic kernels immediately: opaque compute is allowed and is
  needed for performance once Lean emits and checks exact bounded calls.

## Invalidation trigger

Revisit this decision only when Lean emits a closed descriptor that selects an
operation, representation, bounds, and output layout, and Lean checks the exact
returned candidate buffer. That permits a protocol-useful native kernel; it does
not transfer statement, scheduling, or acceptance authority to Rust.
