# Hosted application API controller v2: source checkpoint

This is a **source and Rust-test checkpoint**, not a native event21 acceptance or a deployed agent API. No paid model call or application HTTP delivery was made. The controller route remains opt-in behind an operator-pinned Host image, fixed application/session/ticket/purse route, private operator socket, and enrolled purse signer. A resident transport binding is not a Mini permit; physical delivery still requires the fresh source-owned event21 admission.

The controller retains the model's exact bounded HTTP input and durable forward operation ID before socket I/O. The operator route pins the signed API path (`/repo.git/` in this first profile), app/session/ticket, and separate parent and purse generations. The resident Hello includes these coordinates in its hashed transport binding; they are compared with the pins and do not supply Mini authority. The controller applies the signed prefix once to the caller's relative path. Its reverse `reserve-v2` handler compares every fixed selector and the full routed HTTP request with that retained call, uses the source-owned op58/59 private reserve plan, and submits the resulting call at most once. The original receipt and signed held purse are retained; uncertain reserve replies permit only exact read-only op3 lookup. A confirmed reserve whose journal save preceded the signed purse-coordinate save is recovered by exact lookup and current signed purse read, with the original anchor and generation checked. `inspect-v2` reconciles a lost reverse reply by the forward ID without reposting. `mark-send` requires the SHA-256 of the full source-canonical HTTP request and the confirmed hold before the resident may write to fd3.

For `sign-payer-v2`, the controller re-inspects the resident's paid plan with the pinned Host, requires its full HTTP, context, fixed selectors and reserve index to match the original confirmed reserve, and approves exactly one configured payer signing slot. The private `mini agent-payer-sign` helper separately reauthors the expected paid request, performs a fresh read-only op48, demands byte-exact paid-plan equality, and signs only payer slots. The controller retains and checks the helper's result before returning detached signatures. A partial helper directory is preserved; a later exact-plan request uses a new numbered directory. No partial result is treated as a signature. Hard cancellation/parent disconnect is rechecked before replying.

Read-only HTTP result inspection pins the original host binding across a resident restart. An exact retained HTTP reply is accepted only when its JSON bytes and SHA-256 agree; a host `definite-reply-unverified` retention error remains uncertain and cannot trigger resend. Recovery currently exposes verified bytes for explicit audit; it does not automatically settle a lost response.

The six Rust source paths plus `Cargo.toml` and `Cargo.lock`, with their exact SHA-256 hashes, are in [source-sha256.txt](source-sha256.txt). This manifest includes the recipient-only `shared_app_refs.rs` route that the same runtime cut consumes and the `mcp.rs` relative-path description. The public recipient lookup distinguishes bare event15 from grain-backed event22; the latter stays closed until the typed public op55 route qualifies.

Validation on Darwin arm64 from `native/grain-runtime`:

```sh
CARGO_BUILD_JOBS=2 cargo nextest run
CARGO_BUILD_JOBS=2 cargo clippy --all-targets -- -D warnings
```

The retained [Darwin nextest log](nextest.log) records **112/112 passed** (including an encoded approval larger than 64 KiB, exact-byte retry, and strict retained HTTP recovery). The [Clippy log](clippy.log) records a zero-warning strict check. In an independent hbox Linux source copy, the same eight file hashes passed `CARGO_BUILD_JOBS=2 cargo nextest run` with **116/116 tests** in [the Linux log](nextest-linux.log); that includes the confirmed-reserve crash-state recovery regression and Linux socket tests. The hbox user unit was capped at two Cargo jobs, one CPU and 4 GiB memory. Two earlier Linux attempts were not code verdicts: a non-login unit lacked `cargo`, then the new fixture's socket parent initially had invalid mode. The final `0711` fixture parent passed the same production validation.

These checks establish Rust source behavior only. The Darwin forward-socket `FD_CLOEXEC` race has no deployment qualification in this checkpoint. A source-matched native op46/48/58/59 Host, the resident two-process callback, signed permit, physical send, and exact result/settlement recovery still require separate acceptance evidence.
