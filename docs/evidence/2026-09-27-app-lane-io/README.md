# Proved lane IO, experimental native Host comparison

The [read-only baseline](../2026-09-27-app-latency/README.md) identified Nat/BitVec lane input and output in the 9aec865 Host's cSHAKE256 as a cold replay hotspot. Commit `ecb46aa` adds two general `@[csimp]` equalities in `Compiler/Sp800185Cshake256Core.lean`, source SHA-256 `9810ddac1911c0126c9558d15af61557f60080cf2e7da146ce856543daf616c9`: every block/lane, including missing zero bytes, has the same `laneFromBlock` result using UInt64 shift/XOR; every state/index has the same `stateByte` using UInt64 shift and byte extraction. The existing proved UInt64 24-round permutation is unchanged. Narrow Lean passed; both new axiom reports are `[propext, Quot.sound]`. Generated C SHA-256 `7fa5dce858548dc10a21cf4597c2f71ef39333c407af613c8187342302861f25` uses `lean_uint64_shift_left`, `lean_uint64_xor`, `lean_uint64_shift_right` and `lean_uint64_to_uint8`; `xorRateBlock` and `squeeze32` call the new functions. The C object passed the certified Linux toolchain's production clang flags.

To get a direct native measurement without a second large build, build_native copied the certified 9aec865 Host response file and replaced exactly line 54's old Core object with the new module-path object SHA-256 `a43e364cf5dbbb6cd20016597a40bd7b826fa02cad9af0c164ea41726cc88268`. The other 3,144 entries were unchanged; [response.diff](response.diff) is the exact one-entry diff. The experimental Host linked and printed its expected usage contract. Its SHA-256 is `e73f872a64f01435eb79a0a28a691968f8dc283582cc1addeb12c4e9be36b011`; the certified baseline remains `47e09c5589667ef3f5dc5e630601b85ca4a5a76062509fdf562525dd04aa9a25`. This is a **measurement-only binary**, not a fully recompiled source-certified release: dependent OLeans and C objects remain from 9aec865. Build artifacts are in private `/tmp/mini-core-ecb46aa-experimental*` on Persvati, not installed over the baseline.

Both binaries served the same private copied `run-r3` application Store from `/tmp/mini-app-latency-9aec-DzoGTx`, with the same Mini SHA-256 `29809a46e5cd64d49246ddcbb164012f993d7abd7eb623cafafe654a6ea7e1e7`, same config, authorized subject-8 intent/key, and distinct local sockets/attempt directories. Each first query started a fresh persistent Host and requested the same resource view. A bounded `timeout 240` wrapped each Mini query. [measurements.txt](measurements.txt) preserves the exact selected wall times and hashes:

| Host | First verified read | Same-process later reads |
| --- | ---: | ---: |
| Certified 9aec865 baseline | 58.35 s | Earlier separate run: 1.60, 1.50 s |
| Core-object-only experimental | 42.14 s | 1.10, 1.10 s |

The first-read pair differs by 16.21 s (27.8% of baseline) on this one copied image. All experimental `view.bin` files and the baseline result have the identical SHA-256 `4f129443779669e1966dc594b1dab5f4e2441fa186838948781ad43d40057c1b`; the physical SQLite Store stayed SHA-256 `d1d1fbea3e43aeadcb626d730a28cd81bc4fb28244214b66b063eabf49b756a7`. The view bytes are Host results from signed observations, not independent signed attestations. This is one bounded A/B pair with variable host load, not a throughput distribution or a claim that this cut removes all cold replay cost. The earlier 1.50–1.60 s warm baseline was measured in a different process, so the warm numbers are contextual rather than a matched pair.

Next release gate: compile the complete final source closure with `ecb46aa`, run the same copied-Store read and retained receipt lookup, verify exact query view bytes, historical receipt coordinates and unchanged physical bytes, then time cold/warm again. This object-substitution experiment narrows the cost attribution but cannot replace that full native qualification.
