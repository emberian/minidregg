# Signed GitWeb physical INSTALL handoff (source-only gate)

This cut prepares the existing r3 same-Store journey after its app/session owner releases it. No r3 Store, root inbox, installed image, volume, systemd unit, or HTTP entrance was changed by these checks.

`journey.sh materialize-request` retains the exact event23 BEGIN and event24 claim hashes from `install-prepared-v2.json`, v2 launch root, signed raw GitWeb SPK SHA, app UID, image path, and pinned SPK Host binary. The separately root-run `spk-stage-prepared-inbox` checks that retained request and copies only those SPK bytes to the root:0600 inbox. It neither ingests nor claims an execution receipt. The existing bounded root `spk-ingest` remains the only materializer and is invoked separately after this stage when the image is absent. If the image already exists or ingest's execution reply was lost, the journey does not run ingest again: `adopt-materialized` calls the new read-only `spk-host inspect-installed`, which reparses and checks the installed signed SPK and protected manifest. Its retained adoption says `read-only-current-inspection`, never “ingest executed.” `install-complete` requires this adoption and all original request/image hashes before source event25 completion.

After accepted INSTALL, the root `spk-var-volume create 8401 APP_UID SIZE_MIB SOURCE_VOLUME_HEX` uses only `install-prepared-v2.json.begin.volumeIdHex`. Root `attest 8401` publishes the exact witness. `journey.sh adopt-volume` checks its stable bytes against that source ID, root host/deployment identities, UID, quota and fixed resource/mount; `prepare-resident` requires the unchanged adoption. The resident helper independently rechecks the witness and current Mini completion receipt. These are explicit physical/operator handoffs, not Mini's observation of a root filesystem.

The three pure journey actions use numbered attempts. A crash before the `complete.txt` marker retains the partial directory; a later run chooses a new number, and downstream actions select exactly one completed attempt. The root inbox helper requires a completed materialization request. An existing root inbox file is compared byte-for-byte by SHA and not overwritten. An existing image is adopted by read-only inspection; no missing receipt triggers another materialization.

Scoped validation: `sh -n`, `bash -n`, ShellCheck, `rustfmt --check`, and `git diff --check` passed. An isolated hbox build of the new `spk-host` CLI passed. Its invalid UID and relative-image inputs refused; that snapshot had no installed GitWeb image for a positive call. The exact helper-body recovery test on hbox passed: a partial first request remained, the second completed and was selected, and a third claim refused. The final qualified binary and live signed installed-image inspection are later native gates. The r3 Store remains exclusively owned by client_session until explicit handoff.
