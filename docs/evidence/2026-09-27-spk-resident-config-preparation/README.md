# Resident START config preparation

`scripts/spk-platform/prepare-resident-config.sh` prepares an owner-private `resident.json` for one existing GitWeb app 8401 Store. It accepts four absolute paths: the prepared fixture root, the completed INSTALL journal, a **new** resident journal under `/var/lib/minidregg/spk/resident-ops/`, and an owner-private request JSON. It writes no Mini Store record, signs nothing, and starts no unit. A failed attempt retains its new journal and lookup diagnostics; do not reuse that destination.

The request uses `protocol: "mini-spk-resident-config-request-v1"` and exactly these fields: `spkHost`, `spkHostSha256`, `bwrap`, `bwrapSha256`, `appGid`, `unit`, `startAction`, `entrances`, and `agents`. `unit` is an operator candidate such as `mini-spk-a8401-g2.service`; it is compared with fresh source op66/26 before spawn. For first creation use `startAction: {"kind":"create","index":0}`. For a later wake use `startAction: {"kind":"continue","createdIndex":"..."}` and an additional `createdJournal` path naming the original completed-create resident journal. The script checks that journal's source-selected create action, exact volume ID, retained completion and original op38 marker, then performs a read-only op39 lookup on its exact ingress. The current Mini author must still select the completed-create record and command; `/var` contents and the request file do not decide create versus continue.

`entrances` is a nonempty array of `{directory,dispatchCustody,displayName,preferredHandle}`. Each custody and `directory/custodian.json` must already be private, agree on fixed app/subject/session/ticket/kind, and use one of the reserved Alice Web, Bob Web or Alice API session/ticket pairs. `agents` may be empty; entries use ResidentConfig's fixed `{socket,controllerUid,custody,reverseSocket,routeName,attemptDir,displayName,preferredHandle}` shape and must carry the reserved Hermes A/B app, session and ticket identities plus the candidate unit generation. These checks do not create or imply ticket/session/grant authority. In particular, Bob's app observe cap 184 and Hermes A/B caps 274/374 must be source-granted before their routes can pass native readback; issuer cap 141 is not a substitute.

The script checks `install-prepared-v2.json` against `install-completed-v2.json`, the original op38 ingress/submit marker, signed GitWeb SPK and v2 launch qualifier. It then invokes the pinned Host's **read-only** `application-lifecycle-completion-lookup` on that exact original ingress and requires the replayed four-field receipt to equal the INSTALL completion. It copies the source-inspected `begin.volumeIdHex` into `expectedVolumeId` only after checking the root-owned attestation's deployment, host, resource, app UID, volume ID, quota and mount. Rust reopens/rechecks the attestation before any launch. The config retains the INSTALL Host, Mini config, operator socket and custody paths; the request pins separately qualified SPK-host and bwrap executable bytes. `provenance.json` and `input-sha256.txt` record these pins, every participant custody/policy hash and the read-only lookup alongside `resident.json`; the script compares them again before completion.

This is a staged source/fixture helper. It has not been run against an accepted INSTALL Store, a linked Host/SPK-host pair, a real root volume registration or completed participant custody. Resident START is still guarded until its fresh claim and recovery path are qualified. The retained `checks.txt`, syntax/ShellCheck logs and `refusal.*` record static PASS and an invalid-root refusal with no output directory. The script's exact embedded `--check-request` parser accepts the retained create and continue JSON examples and refuses the same create request with an unknown top-level field; those shape-only checks neither open custody nor establish source authority. `SHA256SUMS` pins the script, examples and logs. No native START or STOP acceptance is claimed here.
