# Persistent Host latency on a copied application Store

This is a bounded read-only measurement on Persvati, 2026-09-27. The Host is the source-certified `9aec865` Linux checkpoint, SHA-256 `47e09c5589667ef3f5dc5e630601b85ca4a5a76062509fdf562525dd04aa9a25` ([build scope](../2026-09-27-native-checkpoint-9aec865/README.md)); Mini is SHA-256 `29809a46e5cd64d49246ddcbb164012f993d7abd7eb623cafafe654a6ea7e1e7`. The configured SQLite helper is the [source-certified `776ba59` binary](../2026-09-27-mini-776-linux-helpers/README.md), SHA-256 `ad03aede839259c1884383fc97f141a3fe106ba2f2cbae0df6f7916676fe193f`. The Store came from mini_app_contract's completed `run-r3` application-birth fixture, originally exercised with an older Host. Only its 536,576-byte SQLite Store, authorized subject-8 read inputs, and retained birth attempt were copied into private mode-0700 `/tmp/mini-app-latency-9aec-DzoGTx`. The copied config changes only `storageRoot` to that copy (config SHA-256 `bf3b4233bfc72d13bb82ecd0abd697ed718372c0fd674e2702363a4483672940`). No active fixture or paid provider was used.

Portable bounded artifacts: [timings.txt](timings.txt), [read-projection.json](read-projection.json), [receipt-projection.json](receipt-projection.json), [identities.txt](identities.txt), and [cold-profile.txt](cold-profile.txt). They contain no config body, private key, or canonical call bytes. The read projection selects only the type, resource ID, and root from each decoded view; the receipt projection selects only the four signed receipt coordinates and outcome type.

The first lookup command rejected in 0.10 s with `config pin mismatch` because the copied attempt still named its original Store config. That is a client transport rejection, not a native lookup measurement. For the successful 1.70 s probe, **only the copied attempt's transport paths** (`config.json` and `attempt.json`) were rebound to the copied Store/new Host socket; its signed `call.bin` was unchanged. This is a controlled exact-call replay under a different transport config path, not an untouched original attempt. The private scratch holds timing files, the two selected receipt projections and physical Store hashes; no key or call bytes are copied into this evidence directory. A concurrent, unrelated application fixture also used CPU on the same host, so these few timings are not a throughput benchmark.

The source explains the large cold/warm split. `NativeHostSession.start` reads the complete image and calls `NativeHostReplay.verifyLoaded`, whose `walk` derives and validates each accepted record before admitting the exact final bytes. Every later state request calls `NativeHostSession.refresh`; an unchanged exact physical readback reuses the verifier-minted tip, while changed bytes must pass canonical load and checked suffix replay. `Host.Main.dispatchSession` uses this path for lookup, challenge and query. One further cold query with `strace -f -c -e trace=process,file` took 79.76 s and produced the same `view.bin` hash. Its process/file syscall time was 0.754 s, including 113 `execve` and 113 `clone` calls; an observed Host process had accumulated approximately 78 s CPU after the query. The selected syscall set excludes read/write and does not profile Lean functions, but it rules out process/file syscalls alone accounting for most cold wall time. Repeated native semantic work is the source-grounded candidate.

The remaining ~1.5–1.7 s warm request includes Mini signing/transport and Host work. One concrete repeated Host cost is `DurableReceiverIO.NativeConfig.read`: **every refresh** launches the SQLite helper's `read-to`, writes a temporary snapshot file, reads the complete BLOB, converts `ByteArray` to `List UInt8`, and compares it after converting both images back to `ByteArray`. The SQLite helper selects the full `opaque_record.bytes` BLOB. A standalone `read-to` of this exact 282,919-byte canonical BLOB finished below `/usr/bin/time`'s 0.01 s resolution, so helper IO alone is **not** shown to dominate the warm request. A bounded optimization experiment should return complete binary bytes through the helper's existing `read` stdout command into a pinned Host binary pipe, retain a `ByteArray` for fast-path equality, and convert to `List UInt8` only when bytes differ. Measure end-to-end warm query before accepting that change. It must bound the pipe body, drain/close it without deadlock, distinguish missing from read failure, and keep the helper executable/config pin. The unchanged-image decision must still compare the complete bytes against the verified tip; a stat, length, mtime, or digest-only cache would not preserve rollback/rewrite detection. Changed bytes must continue through canonical decode, full old-prefix identity and checked suffix admission, and read uncertainty must still poison the session.

For cold replay, the first concrete core seam is `NativeHostReplay.walk`: for each accepted record `advance` constructs/encodes the entire growing canonical image, `validateLoaded` reopens and checks the entire resulting directory/authority/cell/policy state, and each retained receipt computes `imageBoundary` at that prefix. On this 14-record image those repeated full-prefix operations are plausible CPU cost, but no individual function was timed. The next finite change should instrument these three calls in an isolated exact-source build, then replace the dominant one with a general equivalence theorem carrying the same full-prefix `Opened` and receipt evidence. For example, a delta validator must prove the same result as `validateLoaded` for every admitted next image and retain complete physical readback at the final tip; a cheaper unchecked per-record state is insufficient. A persisted checkpoint would additionally need proof-carrying exact old-prefix/receipt and verifier/config identity, not an unverified cached tip.
