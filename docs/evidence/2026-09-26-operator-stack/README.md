# Operator stack installer, Linux component gate

[`install-operator-stack`](../../../deploy/grain-host/install-operator-stack) SHA-256 `85a96c681e2c002b7c6e788a9cd6cd2bd44d0eeadaf4fc6c5b99f405befc553d` and [its runbook](../../../deploy/grain-host/OPERATOR-STACK.md) SHA-256 `21e654e2411fb73d2dcdac6c81f114241912ecbdfbe8ee651fb25348dbe582a8` passed `bash -n` and `shellcheck`. This is a **component** gate for a new private operator service installer, not a claim that the live operator transients have already been replaced or that machine-reboot startup works. The source intentionally refuses `enable` and generated units omit `[Install]` until cross-user boot ordering and durable path migration are qualified.

On persvati, a mode-0600 private manifest pinned the live fresh two-account offering's Mini client, Host, Store/signature helpers, frontend, provider fixture, runtime, per-task configs/unit fragments, and the installer itself. The source-matched `quiescence` action read the exact running UID1001/UID1002 controller image/argv/unit pins, journals, and historical worker units. It passed for both tasks after the three completed Hermes prompts; the operator's original Mini Host remained active.

At installer SHA-256 `0e3dabd91eeb682d528562be2c6bc8e49a24e3c654c05a56c61ebd51380bf63b` (before the final boot-guard split), five **unique inactive scratch** user units were installed into the actual operator manager's load path; an exact second install was idempotent and `systemd-analyze --user verify` passed. A deliberately changed unit file was refused as content drift and the scratch files were removed. No scratch unit opened a Mini socket or provider listener. The later systemd guard probe below used the final `85a96c68…` source.

The final source was then tested through **actual systemd**, not a shell-only guard call. A distinct scratch Host unit used the same two-controller manifest and `NoNewPrivileges=yes`, but its main executable was pinned `/usr/bin/gnutrue` so it could not touch Mini. `systemctl --user start` succeeded with `ExecStartPre=install-operator-stack ... guard`, then the unit exited successfully. After changing only the scratch manifest's pinned Store-helper SHA, a second start failed before its main executable: `Result=exit-code`, `ExecStartPre` status 65, `ExecMainStatus=0`. A separate final-source `start` probe with those scratch units refused **before** launch because the selected live task controller was active. The original manifest was restored and all scratch units removed. [safe.log](safe.log) retains the bounded verdicts. The live Store, Host, frontends, task controllers, and providers were not changed by this probe.

The operator source uses a private signed-root callback for its explicit `restart` action and rejects task journals with live child/pending/held/provider effects or any worker unit with MainPID/cgroup. A full live service transition and that restart path remain a separate acceptance step. Its pins are operator-selected artifact identities checked at install/start/guard/status, not an immutability certificate against a malicious same-UID operator. Separate frontend sockets do not isolate backend availability.
