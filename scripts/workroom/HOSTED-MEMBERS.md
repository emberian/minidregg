# Two hosted members on one Mini content page: wiring contract

Design scope, 2026-09-26. This is the next hosted construction after the signed native `member-acceptance.sh` fixture; it is **not** a report that two controllers have run. The native fixture enrolls subjects 7, 8 and 9, births separate grains, and exercises subjects 8 and 9 on content object 8001. It does not configure a second controller/tool pair. This map uses the current `grain-runtime` config and `mini_read_resource`/`mini_publish` paths; every operation still needs current native Mini admission.

| Role | First friend | Second friend, fresh hosted deployment |
| --- | --- | --- |
| Parent controller signer | subject 7, controller key, parent grain 7801 | subject 9, **different** controller key, parent grain 7803 |
| Hosted tool signer | subject 8, tool key, tool grain 7802 | subject 10, **different** tool key, tool grain 7804 |
| Parent witness | a child capability held by subject 8, pinned to parent 7801 generation | a distinct child capability granted by subject 9 to subject 10, pinned to parent 7803 generation |
| Shared content 8001 | child 95 observe+mutate and sibling 96 observe-only, held by subject 8 | fresh child 97 observe+mutate and sibling 98 observe-only, held by subject 10 |
| Controller custody | private state directory, control socket, parent key, tool key and worker unit for 7801 | **separate** private state directory, control socket, keys and worker unit for 7803 |

These 7801–7804 task IDs are proposed for a **new** hosted deployment, separate from the native member fixture and recovery's 760x IDs. The present native `member-acceptance.sh` assigns children 97/98 to subject **9**, so those grants cannot simply be placed in a subject-10 runtime config or reassigned in that Store. Its grain 7503 also belongs to the native member fixture; no subject-10 enrollment, grain 7804, worker policy or witness delegation exists yet. A hosted fixture must bootstrap/enroll subject 10, birth its tool grain, configure parent 7803's source-authored policy for worker subject 10 and generation 1, and admit the B parent witness grant. Its enrollment must choose an explicit free funding `accountId`: mechanically setting accountId to subject 10 collides with this genesis's factory resource ID 10. The new key, account, capability and resource identifiers need the same distinct-namespace checks as the existing birth. Content owner 7 must delegate scoped B grants on 8001 to subject 10 with distinct capability IDs. The first friend's grants remain independently live. The one shared Store and content cell serialize conflicting edits through their signed expected root and exact old-atom preimage; a native stale edit refusal remains a required corrected-r2 acceptance result. The r1 stale attempt lacked its observe grant and cannot establish that property. Each write grant authorizes edits to the whole content page, including another member's atom; it is not a per-atom ownership rule.

Each controller's `Config` must name its **own** `task`, `subject`, `custodyKey`, `toolTask.task`, `toolTask.subject`, `toolTask.custodyKey`, parent witness capability and fixed `allowedPublications`/`allowedReads` for 8001. For B, the tool publication grant uses B's mutate+observe child 97 and its named read uses B's separate observe-only child 98; A continues to use 95/96. `mini_publish` takes only an allowlisted target and caller payload, then the controller signs a joint tool-grain settle, current parent witness and content mutation with the configured tool signer. `mini_read_resource` signs its selected named read with that tool signer and observe-only grant. A friend must never obtain the other controller's parent/tool key merely to connect to its service. A revoked B content child must make B's next signed read or publication refuse, while A's current grants continue to work; revoke both B children to remove both read and write. Parent/tool fencing is a separate lifecycle action and does not revoke an independently delegated content grant.

For a Linux deployment, run one `mini-grain-controller@<PARENT_TASK>.service` per parent with matching active MainPID. Each has its own 0700 state directory, `control.sock` directly inside it, unique `mini-grain-t<TASK>-o<OP>.service` worker units and launch-gate tombstones. The two controllers may use the same read-only Mini host binary and Store service socket; they must not share custody keys, writable state, worker mounts, control sockets or process-group ownership. Production friend isolation needs separate Unix accounts and forced-key entries fixed to each account's own control socket/mode. If both hosted Hermes workers make provider calls, each also needs its own provider task/key, gateway bind and budget; this native content fixture does not establish provider behavior.

The Store owner in this proposed map is still subject 7, whose content control capability 90 governs delegation and revocation. Subject 9 is an independently signing member/controller, not a symmetric co-owner of 8001. Equal governance or member-controlled grant removal would require its own authorized policy/delegation design. A successful next acceptance needs two live controllers with distinct signed parent/tool calls, alternating MCP reads and publications on one content root, a stale-root refusal and reread, then B read/write revocation with A continuing. Signed native member acceptance alone cannot satisfy that hosted claim.
