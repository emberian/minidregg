Architecture

Lean owns semantics and admission. Rust owns the physical boundary. Every change is a proposal, and the Lean kernel admits or refuses it.

authored source + partial specifications
                   ↓
        checked program + pinned profile
                   ↓
authorized inputs → computation → typed effects and results
                   ↓
   current grants · laws · read roots · funding
                   ↓
         admitted durable transition
                   ↓
 views · retained outcomes · delivery · authorized private release

This is the shared contract, not a claim that every arrow is wired for every language and backend.

Admission by re-execution

The Lean kernel admits or refuses each proposed change against current capabilities, laws, exact read roots and funding. It checks a computation by running it again: at admission, and again on every replay when a Store is reopened. No admission uses a proof. The deployed Host's Lean umbrella leaves out the proof-system research, because nothing on the admission path needs it; the Host still imports twelve of its modules through a digest backend.

That research layer is called Selvage: hash-based, small-field machinery for proximity testing, sumcheck, transcript compilation, accumulation and verifiable history. It is research, and it has no role in admission today.

The Rust side supplies clients, signing and custody, storage, transport and hosted-service adapters, and decides nothing semantic.

The store and laws

One Store is one directory with a SQLite log, plus one key file and an anchor for its head kept outside the directory. Every log entry and every checkpoint carries a KMAC tag under the Store's key. A valid tag means this Host executed and accepted this history. It does not mean that every signed request was admitted again.

What lives in the store are resources: governed state with an exact current representation and history. Access is by capability: an owner delegates a grant with specific verbs to another member, and can revoke it, after which the holder's next request is refused revoked. Each resource also has a law, a predicate the Host checks on every change. Laws are written in JSON or, on main, a one-line grammar, and on main the Host can say before installation whether a law can ever be satisfied. A law can lock a resource for good:

mini> law lock notes {"type":"any","predicates":[]} --allow-unsatisfiable   # "any of nothing": denies everything
mini> submit lock
mini> read notes                                       # refused: law-denied: sealed   (exit 3)
mini> law unlock notes {"type":"all","predicates":[]}  # refused: law-denied: …

Neither the owner nor the operator can get past that law. A capability and a law are separate: neither is replaced by an object reference.

Turns and receipts

Every action is a signed request. An admitted one leaves a receipt with a confirmation (installed, replayed or recoveredAfterUncertainResponse), a transaction id, an event id, an accepted count and the resulting world root. A refused one names its reason from a closed set: no-grant, unknown-key, law-denied, revoked, stale-root, stale-grant, bad-signature, malformed, operation-rejected, conflict, outside-validity, law-input-range, tail-bound and undisclosed.

A lost reply is answered by looking up the same call bytes, never by sending a new request. Retrying after a restart returns the same receipt, with replayed and the same transaction id.

The SDK and the consent boundary

The client SDK (a Rust crate, and a TypeScript package that matches the Rust core byte for byte) is how an app, an agent, a bot or a browser extension asks the world to act for a member without the member's key ever signing bytes the member did not see:

Profile ─► Intent (one typed cut) ─► explain() ─► Confirmation (nonce-bound)
        ─► sign (only consent-returned headers, only under the Confirmation) ─► sealed call
        ─► submit ─► Receipt | Refused | Uncertain ─► lookup (the SAME call bytes)
  • It runs on the member's device, and key material never leaves it.
  • It trusts a local Host image and consent executable that the member selects, never ones the operator chooses.
  • It does not trust the operator. Before a key signs, the Lean consent process re-derives the plan from the retained intent and returns the exact header bytes this key may sign. The SDK signs those bytes and nothing else.
  • A confirmation is for one invocation, attempt, intent, plan, header list and reading; change any of them and nothing signs.
  • A browser has no consent process. Until a bridge to a member-held replica exists, a browser surface must not sign Mini plans.

Private rooms

Devnet quality; privacy not audited. Private rooms are on main only, not on the public node, and no run on a real Host is recorded.

A room is a resource that other things are born in. In a private room, what a member says is sealed on their own machine under the room key before it leaves. The node holds that key only wrapped to each member. Each wrap is to an X25519 + ML-KEM-768 pair, so what a recorded wrap protects is post-quantum; the signatures that vouch for the founder are not. Kicking a member revokes their grant and makes a fresh room key for everyone else: they keep what they could already read and get nothing new.

What it does not hide, or does not stop:

  • The node sees who is in the room, who wrote when, and how big each line is, in 64-byte steps.
  • The founder key is pinned trust-on-first-use. If it reached a member through the node and nobody compared fingerprints, the node could have substituted its own key.
  • A misbehaving node can hide a key change from a member until that member has seen it once, so a member who has not synced since a kick can be kept on the old key.
  • In the hosted shell the member's key and the room key are files on the operator's box, so a private room needs mini on the member's own machine.

The agreement mesh

The agreement mesh is a Generic Simplex BFT engine written in Lean and compiled native, so that a world can be replicated across replicas that agree on its history. Its model is a fixed committee of n = 3f + 1 with at most f Byzantine members, authenticated reliable delivery and partial synchrony.

  • Built: the engine, and a safety theorem over the Lean engine model. A four-node native harness passes with real TCP, ML-DSA signatures, selective Byzantine COMMIT delivery, durable certificate recovery after restart, and lost compare-and-swap replies.
  • Not built or not shown: liveness is not established. The executed run had four replicas on one host, which is one failure domain. Changing membership is separate work, and the workdesk fixture has not run.

Other parts, briefly

  • Hosted applications (SPK). Sandstorm-style packages run as grains under Mini authority. Install, start, supervised restart and export are integrated on development worlds; no application has served a browser session yet.
  • Hermes. Agents summoned into a room with selected context and delegated tools. Run only with a scripted provider on a private Store; off on the public node.
  • Traffic privacy. A post-quantum onion cohort with cover traffic, executed on one host with an honest registrar; the endpoint sees the plaintext call, and there is no anonymity proof.
  • MPC and FHE. Research: an MPC width-8 adder over private inputs, and FHE on a public two-input expression with one owner.

What is not done

  • No Objective Bend program has produced a native accepted receipt on main.
  • No kernel delivers a response to a yielded activity or persists its checkpoint.
  • The Objective Bend proofs are not checked by the default build.
  • Chat is compiled, with no recorded run joining it to a native Host.
  • Studio has no member-reachable route.
  • Payments ran only on fixtures; nothing is deployed and no mainnet transaction has been made.
  • None of the private execution paths runs a member's program privately.
  • Agreement liveness, and more than one failure domain.
