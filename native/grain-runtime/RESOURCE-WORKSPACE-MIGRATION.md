# Hermes resource workspace migration boundary

Owner: Mini grain-runtime and resource-client maintainers. The `toolTask.resourceWorkspace` directory is installed by the controller operator as a private direct child of `stateDir`; its `workspace.json` must pin the same Host image, config, socket, delegated tool subject, and tool custody key as the runtime config. Hermes supplies named references and typed proposal fields rather than selecting keys, filesystem paths, or raw authority identifiers. Returned signed views may contain resource IDs and provenance; those values do not grant authority. The resource client resolves a name using signed current observations, authors an exact intent, and retains the call and outcome. Grain-runtime reserves the delegated tool allowance and writes a pending operation marker before invoking the client, then settles only after a definite native result or exact lookup. A hard disconnect cancels the child and leaves an uncertain marker for recovery.

The legacy `mini_publish`, `mini_read_resource`, and fixed `mini_create_resource` routes remain for existing deployments and their retained acceptance evidence. When a workspace includes a pinned birth context and namespace root, Hermes advertises `mini_workspace_create` and suppresses `mini_create_resource`; the controller also refuses a direct fixed-family resource birth call. Application and session birth families remain separate because the common workspace currently addresses Mini resources, not their application/session composite routes. A workspace without birth pins can still use named read, describe, propose, submit, and recover while fixed resource birth remains available for its configured families.

The workspace proposal action `delegate` can be authored and submitted by Hermes, but Hermes has no recipient-reference export or import tool yet. The resource-client CLI retains that separate `publish-delegation` / recipient import step. A confirmed delegation submission is therefore not evidence that another Hermes grain can discover or use the child; a receiving participant consumer must be exercised separately.

Delete the fixed resource-birth twin only after a source-qualified Host and current resource client pass an end-to-end controller journey for workspace create and recovery, including lost reply, hard disconnect, changed source/config, forged attempt path, and current-law refusal, and after existing operators migrate their pinned family configs. Historical fixture directories and their receipts remain evidence of the older boundary; do not rewrite them as proof of the new path.
